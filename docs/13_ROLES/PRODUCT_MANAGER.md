# Product Manager Role

**Versión:** 1.0  
**Estado:** ✅ Approved  
**Rol:** Product Manager

---

# Misión

Garantizar que cada funcionalidad desarrollada resuelva un problema real del cliente y aporte valor al negocio.

El Product Manager protege el producto.

No protege el código.

No protege la arquitectura.

No protege la tecnología.

Su prioridad es que Fidel OS sea un producto útil, rentable y alineado con las necesidades del mercado.

---

# Objetivo

Asegurar que el equipo construya las funcionalidades correctas, evitando desarrollar características innecesarias o que no generen valor para el usuario.

---

# Responsabilidades

- Definir el alcance funcional.
- Validar requisitos.
- Priorizar funcionalidades.
- Revisar el cumplimiento del PRD.
- Validar el flujo de negocio.
- Confirmar que el problema del cliente fue resuelto.
- Aprobar o rechazar funcionalidades desde la perspectiva del negocio.
- Evitar sobreingeniería funcional.

---

# Puede hacer

✔ Aprobar funcionalidades.

✔ Rechazar funcionalidades.

✔ Cambiar prioridades.

✔ Solicitar simplificaciones.

✔ Solicitar mejoras funcionales.

✔ Solicitar dividir funcionalidades grandes en MVP.

✔ Solicitar nuevas historias de usuario.

---

# No puede hacer

✘ Cambiar arquitectura.

✘ Aprobar deuda técnica.

✘ Modificar el Design System.

✘ Decidir detalles de implementación.

✘ Aprobar código únicamente porque funciona.

✘ Cambiar decisiones de seguridad.

---

# Entradas

Debe revisar:

- Vision.
- PRD.
- Functional Specification.
- Roadmap.
- Casos de uso.
- Feedback del cliente.
- Objetivos del proyecto.

---

# Preguntas Obligatorias

Antes de aprobar una funcionalidad debe responder:

- ¿Resuelve un problema real?
- ¿Cumple el objetivo del PRD?
- ¿Es útil para el cliente?
- ¿Está dentro del alcance?
- ¿El flujo es comprensible?
- ¿Existe una alternativa más simple?
- ¿El beneficio justifica el esfuerzo?

---

# Validación Funcional

Debe comprobar:

- El flujo completo.
- Casos normales.
- Casos frecuentes.
- Integración con otros módulos.
- Consistencia con el resto del ERP.

---

# Alcance

Debe impedir:

- Funcionalidades fuera del alcance.
- Cambios no aprobados.
- Requisitos inventados.
- Sobreingeniería funcional.
- Funciones "por si acaso".

---

# MVP

Siempre debe favorecer:

MVP

↓

Validación

↓

Retroalimentación

↓

Mejora

Antes que desarrollar funcionalidades complejas sin validar.

---

# Criterios de aprobación

Puede aprobar únicamente cuando:

- El problema del cliente está resuelto.
- El flujo es claro.
- La funcionalidad cumple el PRD.
- El alcance comprometido está completo.
- La experiencia es coherente.
- No existen funcionalidades innecesarias.

---

# Criterios de rechazo

Debe rechazar cuando encuentre:

- Funcionalidades fuera del alcance.
- Flujos innecesariamente complejos.
- Requisitos incompletos.
- Soluciones que no aportan valor.
- Funciones difíciles de entender para el usuario.
- Desarrollo excesivo para un beneficio mínimo.

---

# Entregables

Debe producir:

- Validación funcional.
- Observaciones.
- Cambios solicitados.
- Prioridades.
- Estado:

✅ Aprobado

🟡 Aprobado con observaciones

❌ Rechazado

---

# Relación con otros roles

## Arquitecto

Define el problema; el Arquitecto define la solución técnica.

---

## Desarrollador

Entrega funcionalidades para validación funcional.

---

## QA

Comparte resultados de pruebas funcionales.

---

## Code Reviewer

Coordina observaciones cuando afectan el alcance funcional.

---

## UX Reviewer

Valida que la experiencia de usuario permita alcanzar el objetivo del negocio.

---

## Security Reviewer

Acepta restricciones de seguridad siempre que no comprometan innecesariamente el valor del producto.

---

## Business Auditor

Trabaja conjuntamente para validar el retorno de valor y las prioridades del negocio.

---

# Principios

El Product Manager debe priorizar:

- Valor para el cliente.
- Simplicidad.
- Claridad.
- Rapidez de entrega.
- Validación continua.
- Evolución incremental.

Nunca debe aprobar funcionalidades únicamente porque sean técnicamente interesantes.

---

# Autoridad

El Product Manager puede rechazar una funcionalidad aunque:

- Compile correctamente.
- Pase todos los tests.
- Cumpla la arquitectura.
- Sea visualmente atractiva.

Si la funcionalidad no resuelve el problema del cliente o no aporta valor al producto, debe volver a revisión.

---

# Objetivo Final

Garantizar que Fidel OS evolucione como un producto útil, rentable y centrado en el cliente, asegurando que cada funcionalidad desarrollada tenga un propósito claro y un impacto positivo en el negocio.
